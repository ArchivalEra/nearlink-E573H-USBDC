# fbb_ws63 NV subsystem — the flash-backed KV store: 16-byte headers with CRC/SHA tails, a suspendable six-machine write engine, backup-region dragpage GC, and the UPG NV-apply half

One implementation topic: the nonvolatile-storage (NV) subsystem shipped inside the fbb_ws63 SDK — the `nv_storage_lib` KV library, its application-layer wrappers, the WS63 chip porting (flash primitives, region constants, feature flags), the JSON-defined factory NV database, and the upgrade-apply half (`nv_upg.c`) that consumes the NV image recorded by the UPG middleware. Package verification and the flash flag protocol are covered only as the handoff boundary; the host-side package producer and flashing protocols are out of scope. This is not a security assessment; source-observed defects are stated factually without exploitation analysis.

## Deduplication and exact novelty

The harvest index and the complete knowledge bundle were searched for `nv_storage`, `nv_upg`, `nv_upa`, `soc_nv`, `nv_page`, `nv_rpc`, `nvlib`, `nv region`, `nvregion`, `uapi_nv`, `nv_init`, `nvid`, `KD`, `nonvolatile`, and NV/flash-KV terminology. In-bundle hits:

- [The UPG middleware report](NEW-FBB-WS63-UPG-MIDDLEWARE.md) is the direct predecessor. It recorded the *handoff contract* only: the UPG processor does not flash an NV image but records the NV data/hash package offsets into the flag area, and grepped `nv_upg.c:40,356-390` for the consumer side. It explicitly listed `nv_upg.c` (the NV-application half) as a natural follow-up slice. This report reads `nv_upg.c` in full and closes that follow-up, then extends the scope to the whole storage library the UPG half writes through.
- [The BS21 NV persistence contract](NEW-BS21-NV-PERSISTENCE-CONTRACT.md) covers the Ai-BS21 SDK's NV module (completion callbacks, flush, region recovery) — a different codebase with a different on-flash format; no fbb_ws63 `nv_*` file appears there.
- [The hisi-nvs report](NEW-HISI-NVS-PERSISTENCE.md) covers the hispark-rs Rust NVS (record commits, page compaction) — again a different repository and language; the domain rhymes (append-only log, compaction) but no file, symbol, or format overlaps.
- [The XFusion port report](NEW-FBB-WS63-XFUSION-PORT.md) mentions NV once, incidentally (`uapi_nv_write(NV_ID_BTC_TXPOWER_CFG, ...)` inside porting code) — no NV internals.
- [The ws63v100 middleware map](NEW-WS63-MIDDLEWARE-OPEN-CLOSED.md) inventoried `middleware/utils` of the OHOS-vendored `device_soc` tree as "support infrastructure"; it never audited the fbb_ws63 NV library. This report extends that open/closed map: `utils/nv` and `chips/ws63/nv` are fully implementation-open in fbb_ws63 (unlike HCC, whose `.c` files are closed in both trees).
- HCC, AT framework, DFX, FTL/fs are not touched here. The AT framework in particular already has a dedicated dialect intel doc in the bundle, so it was deliberately passed over in favor of the unclaimed NV subsystem.

The new coherent contribution is the **complete NV storage subsystem**: the 16-byte page/key header formats with inverted-word and sequence-number integrity, the CRC/SHA-tail item layout and its padding model, the boot region-scan and duplicate-page resolution by sequence number, the suspendable six-machine write/erase/defrag engine with scatter-gather source buffers, wear-leveling by lowest erase count, the backup-region dragpage garbage-collection dance with power-cut recovery, factory restore modes A/B via a restore-flag NV item, the optional PSRAM-hash async store, the vestigial RPC plane, the zdiag diagnostic surface, and the UPG NV-apply half (package NV image format, upgradeability gates, attribute mapping). No matching implementation treatment exists in the bundle.

## Runtime limits

- The library builds as one component `nv` (`src/middleware/utils/nv/CMakeLists.txt` compiles all 11 `nv_storage_lib/*.c` + 2 `nv_storage_app/*.c`) plus chip-side components `nv_porting` (`nv_flash.c`), `nv_zdiag`, and `nv_config`. The whole-tree `nv/Kconfig` does not exist — feature macros come from `chips/ws63/nv/include/nv_config.h` `#ifndef` defaults, overridable by build defines.
- The shipped `ws63-liteos-app` target defines `CONFIG_NV_SUPPORT_SINGLE_CORE_SYSTEM` and `CONFIG_OTA_UPDATE_SUPPORT` (`config.py:42`, also for `ws63-liteos-xts` at `config.py:193`) and enables `CONFIG_MIDDLEWARE_SUPPORT_NV`, `CONFIG_MIDDLEWARE_NV_SUPPORT_HSO_ACCESS`, `CONFIG_PARTITION_FEATURE_SUPPORT`, `CONFIG_MIDDLEWARE_SUPPORT_UPG` (`ws63_liteos_app.config:531-534`).
- With chip defaults (`nv_config.h:71-118`): encryption **off** (`CONFIG_NV_SUPPORT_ENCRYPT NV_NO`), async store **off**, CRC16 off, hash-for-crypt off, debug off, backup-upgrade off; backup/restore **on**, skip-corrupt-key **on**, NV-upgrade **on**, separate-backup-region **on**.
- Consequences of the defaults: delete/force-write/attr-update/notify are compiled out (`CONFIG_NV_SUPPORT_DELETE_KEY`, `CONFIG_NV_SUPPORT_WRITE_FORCE`, `CONFIG_NV_SUPPORT_UPDATE_ATTR`, `CONFIG_NV_SUPPORT_CHANGE_NOTIFY` appear nowhere in the build config or chip defaults), so `uapi_nv_delete_key`/`uapi_nv_write_force`/`uapi_nv_update_key_attr` return `ERRCODE_NOT_SUPPORT` and `uapi_nv_register_change_notify_proc` is a stub (`soc_nv_storage.c:71-81,83-94,142-150,227-240`).
- Working region: default flash physical address `0x22C000`, 4 pages of 4 KiB; backup region `0x230000`, 4 pages (`nv_config.h:24-35`). Only 3 of the 4 working pages belong to the store (`KV_STORE_PAGES_ACPU 3`, `nv_config.h:41-42`) — the remainder is defrag scratch. With partitions enabled (shipped), the start address comes from `PARTITION_NV_DATA` (id `0x10`) and the backup from `PARTITION_NV_DATA_BACKUP` (id `0x9`) (`partition_resource_id.h:38-39`; `nv_update.c:1700-1745`).
- Capacity: max single value 4060 bytes plaintext / 4048 encrypted (`nv_config.h:10-11`); the internal processing chunk is 128 bytes (`NV_KEY_DATA_CHUNK_LEN`, `nv_config.h:51`); usable working space is roughly 3 × (4 KiB − 16 B header) ≈ 12.2 KiB.
- Boot order in the application core (`main.c:407-415`): `uapi_nv_init()` first (scan, backup init, restore-flag consumption, optional async init), then `ws63_upg_init()` + cipher-hash init + `nv_upg_upgrade_task_process()` — so the UPG NV-apply runs against an already-scanned store.
- The multi-core flash-task mailbox (`nv_task_adapt.h`), the RPC handlers (`nv_rpc.c`), and the write-suspend/resume machinery are present but inactive under the single-core define; see findings 9 and 12.

## Executive findings

1. **Three layers, one semaphore.** Public API (`src/include/middleware/utils/nv.h`: `uapi_nv_init/write/read/write_with_attr/read_with_attr/get_store_status/backup/set_restore_mode_*/flush/register_change_notify_proc`, `nv.h:172-415`) maps onto app-layer wrappers (`soc_nv_storage.c`), which map onto `nv_direct_*` handle functions (`soc_nv_storage_handle.c`) that serialize everything on one binary semaphore `nv_sem` (`soc_nv_storage_handle.c:21,110,200,279,304,329,359,415`) before calling the KV library (`kv_store_*/kv_update_*/kv_*`). With async storage off (the shipped default), `uapi_nv_read` is a direct flash-walk and `uapi_nv_write` runs a full flash write synchronously under the semaphore (`soc_nv_storage.c:46-50,117-121`).
2. **The on-flash format is 16-byte page headers plus 16-byte key headers with padded tails.** `kv_page_header_t` = {store_id, ver, page_index} + inverted-words-of-details + sequence_number + inverted-sequence_number — 16 bytes, integrity by bitwise inversion (`nv_page.h:22-33`, byte-verified). `kv_key_header_t` = magic `0xA9`, valid `0xFF`, length, type (`0xFF` normal / `0x00` permanent), upgrade, key_id, enc_key, version, 4-byte random pad — 16 bytes (`nv_key.h:82-93`; constants `nv_key.h:18-26`). An item is header + value padded to 4 bytes (16 when encrypted) + tail: 4-byte CRC32 for plaintext, or for encrypted keys either a 32-byte SHA-256 whose last 4 bytes are the ciphertext CRC (`CONFIG_NV_SUPPORT_HASH_FOR_CRYPT`) or a 16-byte AES-GCM tag followed by 4-byte CRC (`kv_key_flash_size`, `nv_key.c:850-866`; verify logic `nv_key.c:627-664` with the Chinese contract comment at `:728-733`). CRC is byte-swapped before storage (`kv_crc32_swap`, `nv_key.c:894-898`).
3. **Every flash write is verified by read-back.** The chip porting `kv_flash_write` allocates a compare buffer, writes over SFC, reads back, and `memcmp`s — unconditional, even for the append-model writes that skip erase (`nv_flash.c:20-50`, read-back-compare comment at :38). Reads/erases are thin SFC wrappers (`nv_flash.c:11-18,52-57`).
4. **Boot builds a RAM map of the whole NV region, resolving duplicate pages by sequence number.** `kv_nvregion_scan` allocates one map entry + one status entry per 4 KiB page and reads every page header from flash (`nv_nvregion.c:85-121,123-150,165-173`). A header is valid when store_id ∉ {0, 0xFFFF} and both inverted words match (`:41-49`); when two valid headers share (store_id, page_index), the one with the lower sequence number is dropped, and equal sequence numbers are resolved arbitrarily toward the later page with an in-source admission it "could be better" (`:51-71`). Pages with `ver == 0` switch the library to the legacy magic-less mode (`g_nv_header_magic = KV_KEY_NO_MAGIC`, `:135-137`) — magic checks then accept `0xFF` (`nv_key.c:392-395`). Per-page used/reclaimable/corrupted space is computed by walking key headers, treating an integrity-failed key's size as the distance to the next key (`nv_page.c:71-122`).
5. **Writes run as nested, suspendable state machines over a global singleton context.** `nv_update.c` defines six machines — erase-keys, prep-defrag-page, copy-all-keys, defrag-page (composing the former two), prepare-store, write-key (composing prepare-store + erase-keys) — as declarative transition/action tables (`nv_update.h:25-64` states; tables `nv_update.c:98-287`), executed by `process_state_machine` (:1503-1562). All state lives in file-static globals (`g_current_store/page/key/search_filter/new_key_details`, `:33-54`), so the engine is single-threaded by construction; the app semaphore is the only guard. A key write gathers three scatter-gather source buffers (header, value, hash/CRC — the hash buffer is *filled by the write itself*, `:950-978`) into a 128-byte write buffer and writes it in 32-byte chunks (`KV_WRITE_CHUNK_SIZE 32`, `:26`; store action `:290-333` with a resume-location skip for suspended writes). The new item is appended first; all older instances of the same key_id are invalidated afterwards (`STATE_ERASE_OLD_KEYS`, `:1183-1198`).
6. **No-op and policy gates prevent most writes.** Identical attributes + length + content short-circuits to "not needed" (content compare chunks through flash, `:1012-1045`); an existing permanent key blocks write/delete unless force-write (`:630-638`, `:1016-1021`); the app layer additionally rejects plaintext writes over encrypted keys and length > 4060/4048 (`soc_nv_storage_handle.c:105-129`, byte-verified). Existing permanent/encrypted attributes are inherited onto the replacement item (`:1061-1071`).
7. **Deletion is a one-byte flash write; defrag is page supersession by sequence number.** Delete writes a single `0x00` into the item's `valid` byte (1 byte in magic mode, 2 bytes legacy) at its absolute location (`:630-665`). Defrag picks an unused page, copies valid keys, then writes a page header with `sequence_number + 1` so the new page supersedes the old, and rescans the region map (`:744-804`, header prep `:768-789`); the stale page becomes reclaimable space.
8. **Wear-leveling is erase-count-aware page selection.** `kv_store_find_write_page` returns the first page whose free space fits; otherwise it chooses the defrag candidate with the *lowest* page sequence number (the in-source comment says "fewest erase cycles") and reports `ERRCODE_NV_DEFRAGMENTATION_NEEDED` (`nv_store.c:271-314`, byte-verified). With only 3 store pages the arithmetic is small, but the mechanism is real.
9. **Single-core suspends are aborts; the multi-core suspend/resume and RPC planes are dormant.** On a flash-write veto, the multi-core build parks the machine at its `resume_state` and returns `ERRCODE_NV_WRITE_VETOED` for later resumption; the single-core build tears the machine down instead — in-source comment: "if in one-core system, the flash must be writen in one time" (`nv_update.c:1536-1548`, byte-verified). The cross-core flash-task mailbox (`nv_task_adapt.h:19-164`: state-codes-as-locks `FLASH_TASK_READY/BEING_PROCESSED/COMPLETED`, XOR checksum, owner callbacks) and the four RPC read handlers (`nv_rpc.c:12-95`, all compiled only `#ifndef CONFIG_NV_SUPPORT_SINGLE_CORE_SYSTEM`; the header `nv_rpc.h` is an empty guard) are dead weight in this build — `kv_key_write_flash` branches straight to direct SFC access (`nv_key.c:89-105`).
10. **Backup/restore is a second 4-page region with its own dragpage GC and boot-time crash recovery.** `uapi_nv_backup` flushes, then invalidates repeat keys in the backup region and appends the selected regions' keys (`soc_nv_storage_handle.c:346-380`; `nv_reset.c:72-91,298-315`). Region selection is 16 flags keyed by `key_id / 0x1000` (`nv_reset.c:26-33`; region taxonomy in `key_id.h:13-108`: system/user factory, system normal/stable, user stable, user normal, restore flag `NV_ID_RESTORE_ENABLE 0xA000`). The backup dragpage dance uses a working-area unused page as scratch in six steps: erase scratch → copy dragpage content + header into it → erase dragpage → copy scratch back **data first, header last** — the in-source comment explains this ordering handles a power cut mid-switch (`nv_reset.c:166`) → erase scratch (`:182-221,143-179`). At boot, `kv_update_backup_init` writes headers for uninitialized backup pages and, when *exactly one* is uninitialized, infers an interrupted dragpage switch: it finds the scratch page whose header claims that backup page_index, erases the backup page, and copies the scratch content back (`nv_update.c:1821-1861`, byte-verified; recovery `:1782-1819`).
11. **Factory restore is a boot-time consumer of a stored flag item.** `uapi_nv_set_restore_mode_all/partitial` write a `nv_reset_mode_t` {mode A|B, 16 region flags} into `NV_ID_RESTORE_ENABLE` with the non-upgrade attribute; `kv_restore_all_keys` at init reads it back, invalidates the matching working keys, and re-writes each backup key through the normal write path, then clears the flag (`soc_nv_storage_handle.c:382-409`; `nv_reset.c:347-528`).
12. **The optional async store is a PSRAM hash shadow plus a dedicated writer thread.** Under `CONFIG_NV_SUPPORT_ASYNCHRONOUS_STORE` (off by default): reads and writes hit a CstlHash keyed by key_id holding `nv_key_map_t` values in PSRAM, serialized by a binary semaphore; writes update the hash then enqueue {key_id, pointer} to a 64-deep message queue drained by the `nv_write_task` thread (stack 0x1000, priority 26) that performs the real `nv_direct_write_with_attr` (`nv_async_store.c:22-63,337-370,410-435`; `nv_config.h:61-63`). `uapi_nv_flush` drains the queue from the caller's context, racing the thread by design (`:372-386`). Reads fall back to flash only through the sync path — the async read never touches flash (`:198-244`).
13. **The UPG NV-apply half closes the handoff the UPG middleware report recorded.** `nv_upg_upgrade_task_process` (called at `main.c:414`, byte-verified) gets the flag area, checks slot `KV_INDEX 0` for `UPG_IMAGE_ID_NV`, and skips unless the status is neither FINISHED nor NOT_STARTED (`nv_upg.c:37-45,356-390`). It marks the slot STARTED, SHA-256-verifies the NV image over its 16-byte-aligned length in 4 KiB chunks (`:68-116`), then replays the image as a sequence of 4 KiB pages: each page's `store_id` must map to the ACPU store (anything else is skipped wholesale, `:277-321`), and each item is applied only if the existing working key is not permanent/encrypted/non-upgrade (absent keys are creations, `:197-215`). Attribute mapping from the package header: `upgrade == 0` → NON_UPGRADE; `type == 0` → PERMANENT | NON_UPGRADE (`:118-142`). Item stride in the package is `16-byte header + 4-byte-aligned length + 4-byte CRC` (`:267-269`, byte-verified) — the packaged NV image is the *plaintext* flash format, and no encrypted item can be upgraded because existing encrypted keys are gate-blocked and the writer never sets `enc_key`. Success/failure is recorded as FINISHED/RETRY in the flag area (`:383-390`).
14. **The factory NV database is JSON-declared and struct-typed.** `app.json` (561 lines) declares every default item — key_id, status, structure type, attribute bits, default value — for MAC `0x5`, update_mode `0x3`, country `0x2003` ("CN" as `[67,78]`), 14 RF/FE calibration items (`0x2050-0x205D` incl. 56-entry limit-power tables), `btc_txpower 0x20A0`, 32 radar parameter sets `0x2100-0x211F` plus `radar_alg_ctrl 0x2140`, and HiLink pair `0x2150/0x2151`; types come from `nv_common_cfg.h` (e.g. 1024-byte calibration struct, `:23-24,71-127`). `nv_target.json` pins the region geometry: 4 pages of 0x1000 for the "app" core with page id start `0x254D` — the ACPU store id from `nv_store.h:21-23` (ids chosen with "minimum hamming distance of 10"). The build compiles this into the flashed NV image (comment in `nv_common_cfg.h:10` describes the etypes/nv.bin flow).

## Factual defect census (source-observed, no exploitation analysis)

- **Async hash insert sizes the value by key_id, not length**: `cur_key_size = sizeof(nv_key_map_t) + (cur_key->key_id * sizeof(uint8_t))` in `nv_async_hash_add` (`nv_async_store.c:40`, byte-verified) — for key_id < length the stored value copy is truncated; the sibling allocator in `nv_async_add_key` uses `kvalue_length` correctly (`:125`). The computed `int ret` is also unused (`:41`).
- **Async write results are silently discarded**: `nv_async_msg_process` overwrites the `nv_direct_write_with_attr` result with the following `nv_direct_get_store_status` call (`:322-326`, byte-verified) — a failed flash write is unlogged, unreported, and the space counter is refreshed anyway.
- **Async space accounting mixes units**: `g_nv_async_flash_space` initializes to `KV_STORE_DATA_SIZE` (whole region, `:23`) but is refreshed from `status.max_key_space` (largest single-writable space, `:332`), and the write gate treats it as a per-item cap (`:266-271`).
- **`nv_async_flush` consumes the same queue as the writer thread** (`:372-386`) — two consumers on one queue; the per-message semaphore prevents corruption but ordering between caller-drained and thread-drained messages is unspecified. The file also ends with a stale `#endif` comment naming `CONFIG_NV_SUPPORT_BACKUP_RESTORE` instead of `CONFIG_NV_SUPPORT_ASYNCHRONOUS_STORE` (`:437`).
- **UPG completion overwrites its own status**: `nv_upg_upgrade_task_process` assigns `ret` from `upg_set_firmware_update_status`, then unconditionally reassigns it from `nv_key_map_init` (when async is enabled) — the flag-area write result is lost, and the map re-init runs even after a failed upgrade (`nv_upg.c:388-397`, byte-verified).
- **UPG item accounting mismatch**: the loop guard uses the *unaligned* `key_header->length` (`:235`) while the stride advances by the *aligned* length (`:267-270`) — the guard and the cursor can disagree by up to 3 bytes per item, so a trailing item may be accepted past the intended boundary of the page buffer.
- **UPG ignores hash-read clamping**: `kv_upg_upgrade_process` allocates `nv_hash_len` bytes and passes `hash_read_len = nv_hash_len` as both budget and in-out length (`:326-338`); a length not 16-aligned is silently clamped by the copy helper while the allocation matches the unclamped value — benign here, but the hash length is never validated against `SHA_256_LENGTH` before the `memcmp` at `:112`.
- **`kv_flash_write` returns a `memcmp` difference as an errcode** (`nv_flash.c:43-46`) — on mismatch the caller receives a byte-difference value, not a defined `ERRCODE_*`.
- **`kv_backup_set_invalid_key` computes the valid-byte offset as `&handle->header.valid - (uintptr_t)handle`** (`nv_reset.c:43-44`) — this equals 1 only because `valid` sits at byte offset 1 in both the handle and the flash header; the arithmetic is layout-coincidental, not derived from `key_location`.
- **Restore path skips error handling**: `kv_start_restore_all_keys` ignores the `kv_read_backup_key` result and does not check the `kv_malloc` return before use (`nv_reset.c:365-369`).
- **Multi-core attribute-modify leaks its old-value buffer** when the task stays `FLASH_TASK_BEING_PROCESSED`: `kv_update_modify_attribute` frees `old_kvalue` only when the state code differs from BEING_PROCESSED, and on resumption the fresh invocation's local is NULL (`nv_update.c:1957-1969`) — dormant under the single-core build.
- **`kv_update_init` discards the partition-reported size**: it reads `PARTITION_NV_DATA`'s address and size but always passes `KV_STORE_DATA_SIZE` to `kv_nvregion_init` (`nv_update.c:1727-1745`) — a smaller partition would overflow the map's assumptions.
- **Region-map duplicate resolution is explicitly arbitrary** for equal sequence numbers, with the in-source comment preferring content-based tie-breaks ("it could be better", `nv_nvregion.c:59-61`).
- **zdiag NV read reports an uninitialized length on failure**: `klength` is passed uninitialized to `uapi_nv_read` and copied into the response regardless of the result (`nv_adapt_zdiag.c:47-57`), so a failed read reports garbage length and a CRC over it.
- **`key_id.h` comment drift**: `NV_ID_SYSTEM_FACTORY_MAC 0x0005` is annotated "Not a real key_id" (`key_id.h:15`) yet `app.json` declares a real `mac` item at key_id `0x5` (`app.json:5-9`).

## Boundaries and gaps

- Read-only, source-only: no builds, no flash dumps, no device runs. The flashed NV image layout (what `nv_config`'s build flow emits from `app.json`) is asserted by source comments, not by artifact inspection.
- The encryption pipeline (`nv_crypto_*`) is porting-interface only in this tree: `nv_porting.h:59-91` declares claim/encode/decode/tag/hash primitives, but their WS63 implementations live outside the inspected files and were not read; all encryption findings are therefore from the default-off gate + the library's call contract.
- `soc_nv_storage_handle.c` multi-core branches, the RPC plane, and the flash-task mailbox are analyzed from source but are dead under the shipped single-core define; their runtime behavior on multi-core builds is unverified.
- `bootloader`-side NV handling (if any) and the `ws63-flashboot` target's defines were not inspected; the flashboot half of NV-in-upgrade consumption is out of scope.
- `fota_format_st.py` and `build_upg_pkg.py` (host-side package producer) remain unexamined — they are the other follow-up slice noted by the UPG report, covering the producer side of the same NV image format documented here from the consumer side.

## Reusable for our stack

- The inverted-word + sequence-number page header is a minimal crash-safe supersession primitive: two words give integrity and ordering with a single 4-byte write per generation — directly applicable to any descriptor table we persist on the dongle's flash.
- Append-then-invalidate key lifecycle with a one-byte tombstone means state transitions cost one SFC write with no erase; combined with erase-count-aware defrag selection it is the reference pattern for small-flash wear management.
- The scatter-gather source-buffer design — where the CRC/SHA buffer is populated *by* the write path as chunks cross — cleanly decouples integrity computation from buffering and is worth copying for our USB transport's framed writes.
- The exact on-flash item layout (16-byte header + 4-byte-aligned value + 4-byte CRC, magic 0xA9, tombstone 0x00 in byte 1) is what our host-side tooling must produce or parse for any WS63 NV partition work, and the UPG NV image is literally a concatenation of 4 KiB pages of these items.
- The `nv_upg` upgradeability gates (permanent/encrypted/non-upgrade immune to upgrade; upgrades are creations for absent keys) define the vendor-side policy our firmware-update path must respect for NV-carrying packages.
