## kernel 态主动实验 #1 — H2D_MSG_SLE_OPEN(=29) 控制传输

实验: `bmRequestType 0x21, bRequest 0x00(HOST_TO_DEV_SEND_MSG), payload 4B LE 1D 00 00 00` → 1-4

结果（两次重复一致）:
- 控制传输本身 **OK**（4 字节发出，设备接受）
- 随后设备 **固件重启回 boot 态**（bcdDevice 0318→0100, speed 480→12, 5EP→2EP）
- INT EP 出现 `LIBUSB_ERROR_IO`（设备 teardown 时有活动）→ 然后 NO_DEVICE
- 1-5 对照组保持 kernel 态未受影响

结论:
- **协议方向正确**（设备接受控制消息并有反应），但 **SLE_OPEN 序列不完整**
- 缺前置: 子代理 B 情报 = kernel 态应先推 customize/NV 数据（`hbsle_hcc_custom_ini_data_buf`, BSLE 消息通道）再 OPEN
- 固件下载可重复执行（1-4 已重灌回 kernel 态 2 次）—— 开发调试不怕搞挂设备
- usbmon 无法开启（debugfs 权限受限，xanmod 内核）→ 无法抓 USB 层流量

待验证: 子代理 C 的完整初始化序列（NV 推送格式 + 消息通道 framing + ack 格式）

## kernel 态初始化序列 (SDK 源码证实, sle_host_register.c:145-165 + customize_bsle.c:682)

完整顺序:
1. `hbsle_hcc_customize_h2d_data_cfg()` → `hbsle_hcc_custom_ini_data_buf()`:
   bulk 数据通道(HCC_CHANNEL_AP) 发 `[hcc头] [bsle_msg_tag{type=0 CUSTOMIZE_DATA, len}] [bfgn_bt_customization_stru]`
   - bsle_msg_tag = uint16 type + uint16 len (4B LE)
   - BSLE_MSG_HCC_TYPE_CUSTOMIZE_DATA = 0 (enum 首值)
   - 总 ≤ BSLE_LARGE_NETBUF_SIZE = 800B
2. 等设备状态: `hbsle_hcc_customize_get_device_status(BSLE_STATUS_CUSTOMIZE_RECEIVED)` (C2H 消息)
3. `hcc_send_message(HCC_CHANNEL_AP, H2D_MSG_SLE_OPEN=29, ...)` → USB 控制传输 0x21/0x00 + 4B LE
4. 等 `BSLE_STATUS_BOOT_FINISH`

→ 我们只做了 3（SLE_OPEN 控制传输），缺 1/2/4 → 设备无配置 → 重启回 boot。
下一轮实验: 先 bulk 发 CUSTOMIZE_DATA(需构造 bfgn_bt_customization_stru, BLE 侧结构,
SLE 是否必须未知) + 监听 C2H 状态 → 再 SLE_OPEN。

## kernel 态实验 #2 — 完整序列（票 07）三轮盲试

轮次（1-4，每次重灌固件后立即跑 kernel-init）:
1. 161B 帧 (pay_len=800) —— BSP_READY ✓, CUSTOMIZE_RECEIVED ✗, SLE_OPEN → 回 boot
2. 161B 帧 (pay_len=149) —— 同上, 但这次**物理断连**（sysfs GONE, Dev 019 重新枚举）
3. 800B 完整 netbuf (usb_package.len=800, pay_len=800, padding) —— 同上, 又物理断连

已稳定确认:
- **D2H_MSG_BSP_READY 稳定抓到**: INT EP 8B `0100000000000000` (bit0) —— 固件下载后设备发活
- SLE_OPEN (控制传输 0x21/req0/29) 后设备**必然 panic 断连**（INT IO err → NO_DEVICE → 重新枚举回 boot 或物理消失）
- INI 推送 3 种帧格式全试, CUSTOMIZE_RECEIVED 从未返回

结论（重要）:
- **userspace 盲试 kernel 态的边界已到**——wire 帧格式穷举不足以建立通道
- 根因推断: kernel 态需要 **hcc 框架上下文**（service 注册/队列状态/netbuf 池，
  真实驱动 hcc_service_init → hcc_tx_data 的 host 侧状态机），libusb 裸推帧缺此上下文
- **验证票 04 决策**: 最终形态 = 内核驱动（hcc 框架源码现成），userspace 只能做
  boot 态握手（票 01 已验证），kernel 态数据通道应交给 Phase 2 内核驱动
- 下一步: 票 06 内核骨架（让 SDK hcc 源码在 x86 编译跑通），不再 libusb 盲试
